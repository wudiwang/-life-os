# 子系统同步协议 (Subsystem Sync Protocol, SSP)

> 版本 v1.0 ｜ 2026-08-05 ｜ 状态：**协议已定，待实现**
> 主脑：人生 OS（life-os）｜ 首个子系统：领航技术工作台（lh-pm-workbench）

### 本版已定的四条决策

| # | 决策 | 说明 |
|---|---|---|
| 1 | **收件箱 + 一句话确认** | 子系统推来的内容先落 `pending`，我回数字才入库。不污染第二大脑 |
| 2 | **确认只走 TG，不做网页页面** | 归档后自然出现在第二大脑/工作页；代价见 §5 |
| 3 | **每个子系统每天限 5 条** | 刻意约束，逼子系统做取舍。允许交白卷 |
| 4 | **v1 只做 `insight` + `todo`** | `signal` 最易成噪音，字段保留、暂不启用（§3） |

## 一、这份协议解决什么问题

我用 AI 搭了不止一个系统。人生 OS 管"我这个人"的大方向；领航工作台管"我在领航做项目经理"这件事的细节；以后还会有交易系统等等。

问题是：**细节在子系统里天天产生，沉淀却要靠我手动搬到主脑**——费脑力、还总结不全、不够深刻。

所以定这份协议，让子系统自己把**提炼后的经验**推给主脑，主脑把**原则和方向**下发给子系统。

### 三条设计铁律

1. **只同步提炼物，不同步原始数据。**
   领航的需求单、工单、日报原文永远留在领航。推给主脑的必须是"想明白之后的一句人话"，附一个链接指回明细。
   *违反这条，第二大脑三个月内必然变成垃圾场。*

2. **主脑管方向，子脑管细节。**
   主脑不复制子系统的表结构，不做子系统的事。主脑只回答"我该往哪走、该关注谁、时间该花在哪"。

3. **不共享数据库密钥。**
   子系统之间、子系统与主脑之间只通过 HTTP + 共享 token 通信。子系统换语言、换技术栈、换数据库，主脑无感。

### 现状（为什么现在做成本很低）

| 已有 | 说明 |
|---|---|
| 两套独立 Supabase | 人生 OS `ciicsrthevczeldnaeeg` / 领航 `hacnmkokgqlpsoawsoai`，天然解耦 |
| 领航每晚流水线 | `scripts/daily_report_local.py` 21:00(北京) 生成个人日报，**现成挂载点** |
| 主脑消化端 | 大仙（TG + 本机 Claude Code）+ `knowledge_notes` 六大分类 + 总纲索引/互链/矛盾标注规则 |
| 主脑战略源 | `life_stage` 表（stage/focus/advice/principle）+ `goals` 表 |

缺的只有：一根上行管子、一根下行管子、一个收件箱。

## 二、总体链路

```
                     ┌──────────────────────────────────┐
   ①上行：经验/待办/信号 │        人生 OS（主脑）             │  ②下行：阶段/原则/目标
  ──────────────────►  │  inbox_items → 大仙 → 你确认 → 归档 │  ──────────────────►
   POST /api/ingest     └──────────────────────────────────┘   GET /api/context
          ▲                                                        │
          │                                                        ▼
   ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
   │ 领航 PM 系统 │      │  交易系统    │      │  未来子系统  │
   └─────────────┘      └─────────────┘      └─────────────┘
```

**下行比上行更值钱。** 上行是"帮我记"，下行是"让子脑站在我的人生战略下说话"——领航的日报在生成建议之前先读一次 `/api/context`，它给的每日建议就不再是就事论事，而是对齐我当前的人生阶段和核心原则。

## 三、上行接口 `POST /api/ingest`

子系统 → 主脑。**只接受提炼物。**

### 鉴权

```
X-Ingest-Token: <SSP_TOKEN>
Content-Type: application/json
```

`SSP_TOKEN` 为一串随机字符串，放两侧环境变量（人生 OS 的 Vercel 环境变量 + 子系统本地/云端 env），**绝不进 git**。校验失败返回 401，不给任何提示信息。

### 请求体

单条对象，或对象数组（一次最多 10 条）。

```json
{
  "source": "lh-pm",
  "source_name": "领航技术工作台",
  "type": "insight",
  "title": "跨部门排期冲突要提前拉产品对齐",
  "content": "YC155 这次排期跟产品侧撞了三天。事后补救花了 3 天返工，如果在评审节点就拉产品一起过一遍排期，成本是半小时。规律：跨部门的冲突，成本随发现时间指数上升。",
  "category": "项目管理",
  "tags": ["排期", "跨部门", "教训"],
  "occurred_at": "2026-08-05T21:05:00+08:00",
  "link": "https://lh-pm-workbench.vercel.app/?dev=155",
  "dedupe_key": "lh-pm:insight:2026-08-05:1",
  "confidence": 0.8
}
```

### 字段规范

| 字段 | 必填 | 类型 | 说明 |
|---|---|---|---|
| `source` | ✅ | string | 子系统标识，小写短横线。须在 `subsystems` 注册表中存在，否则 403 |
| `source_name` | | string | 展示名，缺省取注册表 |
| `type` | ✅ | enum | `insight` / `todo` / `signal`，见下表 |
| `title` | ✅ | string | ≤ 40 字，一句话说清是什么 |
| `content` | ✅ | string | 200–800 字为宜。**写规律和判断，不写流水账** |
| `category` | | enum | 仅 `insight` 用，见「分类映射」 |
| `tags` | | string[] | ≤ 5 个 |
| `occurred_at` | | ISO8601 | 事情发生时间（带时区），缺省 = 到达时间 |
| `link` | | url | 回指子系统明细页 |
| `priority` | | enum | 仅 `todo` 用：`high`/`mid`/`low` |
| `due_date` | | date | 仅 `todo` 用 |
| `metrics` | | object | 仅 `signal` 用，任意 KV，如 `{"加班天数":5}`（v1 预留，暂不启用） |
| `dedupe_key` | ✅ | string | 幂等键，建议 `<source>:<type>:<日期>:<序号>`。重复推送直接返回已存在记录，不新建 |
| `confidence` | | 0–1 | 子系统对这条价值的自评，< 0.5 的进收件箱但排在后面 |

### 三种 type

| type | 含义 | 收件箱确认后落到 |
|---|---|---|
| `insight` | 经验、教训、规律、值得沉淀的判断 | `knowledge_notes` |
| `todo` | 需要我**本人**出面/决策的事（子系统自己能处理的不要推） | `work_todos` |
| ~~`signal`~~ | 状态信号：投入分布、连续加班、关键人协作频次 | **v1 不启用**，见下 |

> **v1 只做 `insight` 和 `todo`。** `signal` 最容易变成噪音——"本周投入分布"这类数据推过来我大概率不看，却要占掉每日配额。字段规范先保留在协议里（`type` 枚举与 `metrics` 字段都已定义），跑两周后如果确实想要状态感知再开启，属于"只增不改"的兼容变更，主脑代码不用重构。

### 分类映射（`insight` → `knowledge_notes.category`）

必须精确命中主脑已有分类，不得新造：

`项目管理` · `交易迭代` · `生活感悟` · `健康知识` · `人际关系` · `文档模板`

拿不准填空，由大仙在归档时判定并问我。

### 响应

```json
{ "ok": true, "id": "uuid", "status": "pending" }
{ "ok": true, "id": "uuid", "status": "duplicate" }
{ "ok": false, "error": "unknown_source" }
```

### 配额（防噪音）

- 单个 `source` **每天最多 5 条**，超出返回 `429` 并丢弃。
- 这是刻意的约束：逼子系统做取舍，只推最值得的。宁缺毋滥。

## 四、下行接口 `GET /api/context`

主脑 → 子系统。子系统的 agent 在生成日报/建议/决策前先读，用于对齐。

同 token 鉴权。响应：

```json
{
  "generated_at": "2026-08-05T21:00:00+08:00",
  "stage": "…life_stage(field=stage) 当前人生阶段…",
  "focus": "…life_stage(field=focus) 当前聚焦…",
  "principles": ["思维的迭代（关注迭代而非轮回）"],
  "goals": [
    { "title": "…", "level": "quarter", "due_date": "2026-09-30", "status": "active" }
  ],
  "key_people": [
    { "name": "…", "rel_type": "friend", "closeness": 5, "days_since_contact": 47 }
  ],
  "open_todos": 5
}
```

**只读、只出提炼后的战略层信息**，不出日记、健康、情感明细——子系统没有必要知道那些。

### 子系统怎么用它

领航的日报提示词加一段：

> 在给出今日建议前，先读 `/api/context`。你的建议必须与用户当前的人生阶段、核心原则、本季目标一致；若今天的工作安排与其冲突，明确指出冲突。

## 五、收件箱与确认流程

### 确认渠道：**只走 TG，不做网页收件箱页面**

`inbox_items` 是纯后台队列，人生 OS 网页端**不新增页面**。理由：

- 待确认状态最多存在一晚，我在 TG 上一句话就处理完了，为它做一套双端页面不划算；
- 一旦 `archived`，内容就落进 `knowledge_notes` / `work_todos`，在第二大脑页和工作页正常可见——**该看见的地方都看得见**；
- `dropped` 的东西本来就不该再占我的视线。

代价：`pending` / `dropped` 的原文只能在 TG 里查（大仙可随时 `list inbox_items` 翻出来），不影响主流程。

### 状态机

```
   POST /api/ingest
          │
          ▼
      [pending] ──── 我回复序号 ────► [archived]  → 已写入目标表，记 target_table/target_id
          │
          ├───────── 我回复 x ─────► [dropped]
          │
          └── 7 天无人处理 ────────► [expired]   （大仙提一次，不再打扰）
```

### 每日确认（大仙的活）

次日早上，大仙在 TG 推一条：

> 昨天领航沉淀了 3 条：
> 1) 跨部门排期冲突的教训
> 2) 张工的协作方式
> 3) YC155 验收待办（需你出面，8/10 前）
> 回「1 3」存档，「x」全丢，「2 详情」看全文。

指令集（大仙需支持）：`1 3` 存档指定项 · `all` 全存 · `x` 全丢 · `2 详情` 看全文 · `收件箱` 随时手动调出待办列表。

### 推送机制（`tg-bot.mjs` 需改造）

⚠️ 现状：大仙是**纯被动**的——`scripts/tg-bot.mjs` 只有长轮询收消息的主循环，没有任何定时器，不会主动找我说话。TG 单渠道确认必须先补这个能力。

**方案：在 bot 主循环里加一个轻量定时器**（不引入 Vercel cron）。

理由：确认动作本身强依赖本机 bot 在跑（归档要调 `db.mjs` 写库、要走大仙的分类/互链/矛盾标注判断）。既然确认必须本机在线，早报也放本机最一致——**不会出现"早报推来了但没人能处理"的空转**。

行为约定：

- 每 10 分钟检查一次：若当前是北京时间 08:00–10:00 且今天还没推过 → 查 `inbox_items(status=pending)` → 推汇总；
- 推过的日期记在 `scripts/.tg-push.json`（与 `.tg-session.json` 同级），避免重复；
- **本机关机期间不丢**：pending 一直攒着，下次开机 bot 起来就一次性推出来（可能一条汇总里带两三天的量，可接受）；
- 汇总文案由模板拼装，不过 claude CLI（省一次调用，也更稳）；**只有确认后的归档才走大仙**。

> 附带收益：这个定时器一旦有了，生日提醒、60 天失联提醒、检查点到期提醒都能挂上去——目前这些只在网页端展示，我不打开就看不到。

**我只需要回几个数字。** 脑力消耗接近零，但第二大脑不会被机器写的平庸内容污染。

### 归档时大仙必须做的（复用已有规则）

1. `category` 精确匹配，落 `knowledge_notes`，`source` 填 `子系统：领航`；
2. 更新该分类**总纲笔记**的索引清单，加一行；
3. **互链**：先 list 同分类已有标题，相关的在正文末尾加「相关：《某笔记》」；
4. **矛盾标注**：若与旧笔记冲突，正文写明「与《旧笔记》观点冲突：…」并当场告诉我。

> 第 4 条在跨系统场景下价值最高——领航总结的新经验跟我半年前的旧判断打架时，那才是真正的认知迭代点，不能让它悄悄覆盖过去。

| `enabled` | 关掉即静默拒收 |

## 八、附录：待建表 DDL（`supabase/v6_ssp.sql`，确认后由我在 SQL Editor 手动执行）

```sql
-- v6: 子系统同步协议（SSP）—— 收件箱 + 子系统注册表
create table if not exists subsystems (
  id uuid primary key default gen_random_uuid(),
  key text unique not null,
  name text not null,
  base_url text,
  default_category text,
  daily_quota int default 5,
  enabled boolean default true,
  note text,
  created_at timestamptz default now()
);
alter table subsystems disable row level security;

create table if not exists inbox_items (
  id uuid primary key default gen_random_uuid(),
  source text not null,
  source_name text,
  type text not null,               -- insight / todo / signal
  title text not null,
  content text,
  category text,
  tags text[],
  occurred_at timestamptz,
  link text,
  priority text,                    -- todo: high/mid/low
  due_date date,
  metrics jsonb,                    -- signal
  confidence numeric,
  dedupe_key text unique not null,
  status text default 'pending',    -- pending/archived/dropped/expired
  target_table text,
  target_id uuid,
  reviewed_at timestamptz,
  created_at timestamptz default now()
);
alter table inbox_items disable row level security;
create index if not exists idx_inbox_status on inbox_items(status, created_at desc);

insert into subsystems (key, name, base_url, default_category, note)
values ('lh-pm', '领航技术工作台', 'https://lh-pm-workbench.vercel.app', '项目管理', '我在领航做项目经理这件事的细节层')
on conflict (key) do nothing;
```

新表需同步加入 `src/lib/constants.js` 的 `ALL_TABLES`（备份导出用）。
