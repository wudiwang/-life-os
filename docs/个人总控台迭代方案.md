# 个人总控台迭代方案

日期：2026-09-07。
状态：分阶段实施中。首批首页与同步修复已完成本地验证，具体发布情况见后续验收记录；其余清单不代表已实现。

## 产品目标

人生 OS 是个人工作、学习、生活与能力成长的总控台。用户通过当前对话安排和推进不同项目，系统沉淀经过核实的进展、想法和经验，网页呈现目标、时间安排、下一步与需要本人决定的事项。

提升使用价值以减少重复记录、帮助安排下一步和复用已有经验为目标，不以增加填表次数或页面停留时间为目标。仅采集用户指定项目和主动提供的内容，不默认进行全设备行为追踪。

## 已核实的基础

- 当前有效代码在本目录所属的 GitHub 仓库，React + Vite + Supabase；Mac 克隆后与远端 main 一致，依赖安装与生产构建已通过。
- 旧 Next.js 应用已保留于上级目录的 `.codex-backups/legacy-app-2026-09-07/`。
- 首页已有原则、行为契约、每日三向、待办和目标；每日一记已有自由输入、主线、启示和历史记录。
- `docs/子系统同步协议.md` 标注协议待实现，本次未在代码中找到对应的通用收件箱、子系统注册和上下行接口实现。
- `scripts/sync-project-progress.mjs` 目前只配置 Windows 上的交易项目；Git 同步代码不等于同步数据库、环境变量、视频或计划任务。

## 优化顺序

1. 统一输入：一次自然表达保留原话，再提炼候选记录、待办与经验。展示保存、处理中、失败和待确认状态；已有记录可修改、忽略，避免重复生成。
2. 项目总览：统一项目标识，关联人生方向、目标、下一步、阻塞、截止日期、来源及最后同步时间。工作、学习等项目可配置，项目不必是代码仓库。
3. 自动汇入：先接通一个指定项目的成果回传，区分计划、尝试、已验证成果和 AI 推测。用来源标识和事件标识去重，失败可重试。
4. 时间安排：计划投入与实际投入分别保存。实际时间来源于用户确认或明确的计时记录，不以 Git 提交量、电脑开机时长估算。
5. 经验复用：在当前任务上下文中呈现相关历史经验及来源，允许用户纠正结论；周复盘聚合进展、投入、阻塞和下一步。

首页建议围绕今天的重点、项目进展、待决定事项和快速记录组织。既有健康、关系和知识模块保留为专题入口。需要通过实际试用验证使用率低的原因，不能把本次推断当作已证实的用户行为结论。

## 表达训练模块

### 训练闭环

选择本次主题和一个训练重点 → 自录或导入视频 → 从听众角度回看 → 记录观察与真实反馈 → 确定下次一个改进点 → 同题复录比较。

初始训练重点可包括结论是否清楚、结构是否连贯、语速与停顿、口头禅和镜头交流。评价聚焦可观察的表达行为，不根据外貌、声音推断人格或能力。

### 第一版范围

- 新建训练：主题、日期、可选关联项目、这次想练的一点。
- 视频：浏览器支持时录制，并支持导入已有视频；相机或麦克风不可用时保留导入入口。录制由用户主动启动，可停止、预览、重录和保存。
- 回看：原视频播放、暂停、倍速、时间点备注；不自动播放。
- 自评：一个做得好的地方、一个需要改进的地方。评分可选，不能用打分替代具体观察。
- 他人反馈：用户主动录入反馈原意、来源和对应时间点；与自评、AI 建议明确区分，不自动联系他人或公开视频。
- 下一次：只选一个具体改进动作，可关联待办或行为契约。
- 历史：按主题与项目筛选；同题多次训练可切换比较，并保留每次反馈。
- 数据导出：训练记录可导出；视频需明确备份方式、存储位置和删除行为。

先把一次练习做完，再补充复盘。初次保存不强制填写全部评价字段。AI 转写与分析属于后续可选能力，需先确认处理服务、数据去向与成本，不能把尚未接通的能力显示为可用。

### 关联方式

- 训练记录关联统一项目与可选目标；长期表达训练可独立成为学习项目。
- 时长区分视频时长与练习总投入，不能把两者混为一谈。
- 经过用户保留的可复用经验进入第二大脑，并回链训练来源。
- 看板展示下一次练习与最近一个改进点，避免只增加次数统计。

### 数据与部署要求

训练记录、视频资源、时间点备注和反馈分开建模。沿用统一数据访问层，新增页面登记到现有页面注册表；新增表纳入备份。

现有通用文件上传返回公共附件链接，不适合作为私人训练视频的默认存储。上线前需完成私有存储、访问授权、限时播放地址及体积和格式限制。未经验证不能宣称跨设备播放、云端持久保存或视频分析已可用。

Mac 接手后台任务时需处理设备路径配置、任务唯一领取、重试及在线状态，避免 Windows 与 Mac 同时执行产生重复归档。

### 验收

- 桌面与手机均可完成导入、保存、回看、补反馈与安排下一次练习。
- 拒绝摄像头权限、离线、视频过大、上传失败和保存失败均不误报成功，已输入内容可恢复。
- 关闭训练页后释放摄像头和麦克风；原视频不会自动公开或发给其他人。
- 自评、他人反馈、AI 建议具有清楚的来源和状态。
- 完成一次训练后，看板上的下一步与训练记录保持关联。

## 分阶段交付

分析阶段已完成，用户已批准执行并要求发布首批改动。表达训练是后续模块需求，不应抢占总控闭环的首要优先级。

第一阶段先跑通一至两个项目的事实汇入与每日收纳，减少人工搬运。
第二阶段增加跨项目总览、计划与实际时间、下次动作关联，并接入表达训练。
第三阶段在真实记录积累后增加情境检索、同题比较与可选 AI 辅助。

观察指标包括一次记录需要的操作数、自动汇入后需要修改的比例、重复记录数、训练回看完成情况、下一步是否实际推进，以及历史经验是否被重新使用。阈值在基线采集后确定，不凭空设定。

## 优缺点与使用率假设

优势：目标、习惯、随笔、主线与知识库已有可复用基础；有云端数据层；已明确主系统管理方向、子系统保留细节的设计原则。

不足：跨项目反馈尚未完整接通；入口按生活分类组织，但尚未形成清晰的统一项目总览；用户在其他项目做完事情后，可能仍需再次录入；当前采集偏向代码活动，难以覆盖阅读、研究、会议、练习与生活；本机任务离线状态与处理失败需要更直接地反馈。

使用率低的待验证假设：记录成本较高、回看没有立即影响当天决策、入口分散，以及电脑后台不可用时得不到及时反馈。不能从旧记录日期推断用户近期没有实际工作，也不能把多打开网页等同于效率提升。

## Codex 项目关联方案

本次通过应用项目列表确认可见的候选包括 `lh-pm-workbench`、`trade`、`尼日利亚市场`，以及独立任务“面试表达训练建议”。这仅验证可发现性，不代表已经读取各项目全部内容、完成归类或启用自动同步。Windows 本地未推送的代码和该设备独有的任务内容不能假定在 Mac 可见。

建立“人生项目—Codex 项目或任务—仓库或成果来源”的明确映射，不仅凭目录名判断归属。工作、学习、爱好、生活作为可调整的分类；一个人生项目可以关联多个任务，也允许完全没有 Git 仓库。

每日只汇入以下摘要，详细内容留在原项目：

- 今天推进或完成了什么。
- 有什么可核实成果及回到来源的入口。
- 当前阻塞或需要用户决定的事项。
- 下一步具体动作。
- 值得保留的经验，没有则留空。

每条摘要附来源、日期、采集时间和证据状态。没有可见活动时显示“未采集到记录”，不显示“什么都没做”。重复执行不重复入库，补到新事实时更新摘要并保留修订痕迹。

采集采用用户明确选定的范围：可访问的任务总结、成果文件及 Git 事实相互补充；不依赖原始对话全量搬运，也不把单纯提交量作为产出。先用一次手动汇总验收准确性，再启用定时采集。定时任务需要另外实际配置并验证，本方案未创建任何自动化。

## 每日使用闭环

- 开始一天：看今天最重要的一至三项事项与必要的时间安排。
- 工作过程中：仍在原项目推进；临时想法通过一个入口记录，不要求切换多张表。
- 收尾时：系统形成当天摘要，用户只补遗漏和纠正关键误差，选择明天第一件事。
- 每周回看：比较计划与实际、决定哪些项目继续或暂停、找出一条可复用经验。

建议先进行七天小范围试用，再决定扩展。观察是否减少漏事和重复汇报、是否更快确定下一步、已有经验是否真的被复用；不承诺仅靠新增看板就能提升掌控感。

## 主动提醒规则

### 原则

提醒是帮助开始行动或做取舍，不能只是催促打开网站或补齐表格。数字化用于支持决策，不追求完整监控每一分钟。未回复不是失败，也不能被当成已经完成或同意调整计划。

### 触发与回复

| 场景 | 触发依据 | 提醒内容 | 可直接回复的动作 |
| --- | --- | --- | --- |
| 开始一天 | 用户选择的当地时间 | 今天最重要的一至三项及建议先做哪项 | 开始、换一项、延后、今天休息 |
| 约定的练习 | 用户接受的练习安排 | 本次主题与上次待改进的一点 | 开始、改时间、跳过本次 |
| 需要本人决定 | 执行项目返回明确阻塞或审批事项 | 卡在哪里、有哪些可行选择、影响什么 | 选择方案、补充条件、稍后处理 |
| 收尾 | 用户选择的当地时间且有待收尾内容 | 已完成什么、待补什么、明天第一件事候选 | 确认摘要、补一句、纠错、跳过 |
| 周回顾 | 用户选择的每周时段 | 本周推进与时间差异、建议继续或暂停的项目 | 保留、调整、暂停项目 |
| 同步异常 | 持续失败或需要用户处理的首次异常 | 哪个来源未更新、已知影响与恢复办法 | 查看、稍后提醒 |

### 降噪与节奏

- 初始建议仅早间与晚间两个主动触达时段，具体时间、时区与主渠道在启用前确定。本次未设置这些时间。
- 非紧急事项合并到下一次摘要；无变化、无待办且无用户约定的例行检查时保持安静。
- 默认同一事项未回复不连续追催；可让用户选择一次延后提醒，不能自行升级频率。
- 提供免打扰时段、当天休息、暂停单项目、暂停全部，以及提醒频率调整。
- 所有跨设备记录使用统一事件标识；明确哪台设备领取任务，避免 Windows 和 Mac 同时发送。
- 仅在用户选定范围内收集内容；通知默认用简短摘要，不把个人日记、健康或他人信息直接展开到通知预览。
- 展示上次成功同步与来源在线状态，不把“我没收到”归咎于用户没有坚持使用。

### 渠道选择

仓库已有 Telegram 收发和早晚简报脚本，是可复用候选，但不能据代码存在就认定 Mac 已配置或线上正常运行。若用户更常使用当前应用，可评估应用提醒作为入口；任务发现能力不等于后台进程能直接访问所有任务。实现前需要验证可用接口与运行条件，不直接读取应用内部私有数据库来绕过接口。

网页承担回顾与总览，通知承担及时触达，对话承担自然输入和调整。三者应共享事项状态：任一入口处理完，其他入口不继续提醒同一件事。

## 首轮试用与评价

第一轮只接一至两个高频项目。先产生一份可核实日报，再连续试用七天；表达训练作为后续试点，不同时上线全部生活分类。

| 目标 | 观察方式 | 建议试用标准 |
| --- | --- | --- |
| 降低维护成本 | 统计用户主动补录与纠错的时间 | 每天主要确认与补充尽量控制在两分钟内，作为试用目标而非硬性考核 |
| 让自动汇总可靠 | 抽查日报与来源、记录重复和误报 | 不出现无依据的完成结论；发现错误可修正且不被覆盖 |
| 提升下一步清晰度 | 收尾后是否已有可执行下一步 | 至少能明确次日第一件重要事项，允许休息日没有任务 |
| 减少漏事 | 核对待本人决定的事项是否被呈现 | 重要阻塞不埋在其他项目的长对话里 |
| 控制提醒负担 | 用户反馈是否打扰、延后/关闭次数 | 调整或删除无价值提醒，不以回复率惩罚用户 |
| 让经验有用 | 记录经验是否被当前任务引用和纠正 | 能举出实际帮助一次行动或判断的例子，而不只增加笔记数量 |

七天后先决定哪些环节值得保留，再确定第二阶段。使用率应理解为系统是否持续参与有价值的行动与决策，不是每天打开次数越多越好。
